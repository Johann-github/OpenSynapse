## Findings
- (observed) Protocol 3.0 = **BLE GATT**, not USB HID. It uses an 8-byte header (txn,
  24-bit LE length, class, id, profile, region/status) and no checksum. Payloads are
  fragmented into 20-byte writes (legacy) or ≤256-byte header-repeating packets (V2).
- (observed) Protocol 4.0 (USB) = feature report ID 2, 64 bytes. It uses the 2.5 command
  tables, a target device type in transaction bits 5–7, a BE16 size at offsets 4–5, an XOR
  checksum at offset 61, and status `0x0A` for notifications.
- (observed) Protocol choice is static, from the device manifest (`rzDeviceName`,
  `hardwareEventParserType`). The Viper V3 HS is 2.5 / parser 1.
- (observed) Events: byte 0 = record id, byte 1 = event id for records 5/9. The full event
  table is in [[Protocol/Hardware Events]].
- (inferred) The record id is the HID input report ID; the direct HID path defaults to
  report ID 5.
- (observed) `usbUsageEnum` = Consumer-page usages for decoding media keys. It is not
  used to select an interface.
- (observed) The background-manager 4.0 parser reads record and event id both from byte 1.
  The lighting-engine copy reads the record id from byte 0.
