# 2026-11-13 Protocol 4.0 frame and device search

**Question:** Exact 4.0 frame rules for an implementation; which PIDs speak 4.0; can 3.0
go through the HID path?
**Evidence (source / tool):** static reading of `~/re-work/synapse4/pretty/le_33_rzDevice40.js`
(class `rzDevice40`); a script over all of `~/re-work/synapse4/` counting
`rzDeviceName: "<class>"` and `hardwareEventParserType: <n>` values; the 3.0 notes in
[[Protocol/Protocol 3.0 and 4.0]]. No hardware, no captures.

## Findings
- (observed) Checksum = XOR of payload bytes 2..60 at 61 (the 2.5 loop bound runs past the
  63-byte buffer and the checksum is computed before 61/62 are set).
- (observed) Transaction counter 1..31 (never 0), target type in bits 5..7, default Mouse.
- (observed) Status handling, reply matching and timing constants are the 2.5 ones.
- (observed) Device manifests name only `rzDevice25*`, `rzDevice30*`, IoT and audio classes.
  No manifest names `rzDevice40*`; parser types found are 0, 1, 2, 3, 6, 9, 11, 16, 17, 18, 19 —
  none of 26/27/28 (PROTOCOL40). Product bundles contain `rzDevice40*` only inside the
  webpack chunk-name map that every bundle carries.
- (inferred) 3.0's vendor GATT service is not HID-over-GATT, so it is not a HID collection on
  Windows.

Written up in [[Protocol/Protocol 3.0 and 4.0]] and [[Decisions/ADR-0015 Protocol 4.0 and 3.0 support]].
